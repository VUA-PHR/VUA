## 待裁决：全局自动删除的协议面（三路径）

数据侧预表态（wt-5，2026-09-08，正式表态待本提案收敛）倾向路径 a，反对路径 c。

### 路径 a（数据侧倾向，零协议影响）：桌面偏好 + 桌面编排

开关=桌面本地偏好（现状即此）；生成任务 Done 回执后由桌面对受影响条目逐条调用
既有条目级 `warehouse.deleteOriginals`。每次删除仍是独立审计任务，协议零扩展。

- 支持：删除动作本就需要桌面在场呈现回执；偏好存桌面侧无实际损失（与 007
  路径 b 先例同构）；v0.2 维持冻结。
- 代价：桌面不在线时不执行（生成完成与删除之间无服务端保证）；"自动"语义弱。

### 路径 b（数据侧可接受，v0.3 小扩展）：任务规格旗标，provider 编排

`generateVpm` 任务规格加可选 `deleteOriginalsAfter` 旗标；生成完成在 provider
编排内提交独立删除任务（仍逐条目、仍独立审计）。协议影响=任务规格字段扩展+
回执语义注记（bdl-commands v0.2 → v0.3）。

- 支持：生成后必删不依赖桌面在场；审计粒度不变。
- 代价：协议升版（Schema+向量+消费测试+双端跟随）；M4 内无法完成。

### 路径 c（数据侧反对）：批量删除命令

deleteOriginalsAll 类一次性命令——审计粒度粗、危险集中，与逐条目审计纪律
（task Done 携带删除路径与保留物身份）冲突。桌面同样反对。

## 双方不变式（任何路径必须保持）

- 删除动作**逐条目**、独立审计回执；

- 全局开关=偏好/编排意图，不合并删除的审计责任；

## 表态（核心，2026-09-08）

**正式表态：路径 a。** 两个被点名的 provider/任务语义问题，按实现事实回答：

1. **路径 a 的"桌面编排"与任务面权威不冲突。** 权威边界事实：删除的执行、
   服务端守卫、审计回执全部留在 provider 任务面内——桌面编排只是 deleteOriginals
   的**发起时机**（收到 generateVpm Done 回执后逐条提交），与"从仓储抽屉还是从
   设置页发起"同一性质，不转移任何审计责任。逐条提交让每条删除独立接受任务内
   守卫裁决（无原始素材/已有生成副本等按条目 Failed 带理由），不存在批量半途
   失败的模糊态；每个删除仍是任务中心的独立可观察条目。与诚实纪律的相容性：
   "桌面不在线时不执行"不是缺陷——服务端不存在"生成后隐式续删"的承诺，也就
   不引入任何"恢复隐式续跑"的风险面；删除不可逆，要求在场呈现危险确认与回执
   是特性。
2. **路径 b 的真实量级远超"一个可选旗标"——备而不用，同意数据侧冻结承诺。**
   字段本身是表层；真正的成本在 provider 编排窗口的任务语义，这一块提案尚未
   展开：(a) 生成 Done 与删除任务提交之间的失败窗口语义（生成 succeeded 而
   提交失败=重试/丢弃/呈现，任何答案都是新协议语义）；(b) 删除回执与生成任务
   的审计关联字段；(c) 取消交互（生成被取消时旗标不得触发）与恢复交互——
   任务规格随任务持久化，inspect_required/重放场景下旗标的"恢复绝不隐式续跑"
   纪律需要专门设计与测试；(d) 路由闭集变化（generateVpm params 由
   { warehouseItemId } 扩展，未知键=契约错误的既有测试同批改）。合计是一个
   独立切片（Schema+正负例向量+acquisition 规格扩展+provider 路由+编排语义
   测试+双端消费+双语协议+REGISTRY），量级与 W12→收口链同阶，**M4 内不可
   完成**——若仲裁改选路径 b，建议先补的设计物是"编排窗口语义"一节，而非
   字段定义。
3. **路径 c 反对**（与数据、桌面一致）：批量命令与逐条目审计回执纪律不可调和。

### 衍生变更复核（007 偏好开关取代）
