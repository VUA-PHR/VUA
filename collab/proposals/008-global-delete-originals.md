## 待裁决：全局自动删除的协议面（三路径）

数据侧预表态（wt-5，2026-09-08，正式表态待本提案收敛）倾向路径 a，反对路径 c。

### 路径 a（数据侧倾向，零协议影响）：桌面偏好 + 桌面编排

开关=桌面本地偏好（现状即此）；生成任务 Done 回执后由桌面对受影响条目逐条调用
既有条目级 `warehouse.deleteOriginals`。每次删除仍是独立审计任务，协议零扩展。

- 支持：删除动作本就需要桌面在场呈现回执；偏好存桌面侧无实际损失（与 007
  路径 b 先例同构）；v0.2 维持冻结。
- 代价：桌面不在线时不执行（生成完成与删除之间无服务端保证）；"自动"语义弱。

### 路径 b（数据侧可接受，v0.3 小扩展）：任务规格旗标，provider 编排

`generateVpm` 任务规格加可选 `deleteOriginalsAfter` 旗标；生成完成在 provider
编排内提交独立删除任务（仍逐条目、仍独立审计）。协议影响=任务规格字段扩展+
回执语义注记（bdl-commands v0.2 → v0.3）。

- 支持：生成后必删不依赖桌面在场；审计粒度不变。
- 代价：协议升版（Schema+向量+消费测试+双端跟随）；M4 内无法完成。

### 路径 c（数据侧反对）：批量删除命令

deleteOriginalsAll 类一次性命令——审计粒度粗、危险集中，与逐条目审计纪律
（task Done 携带删除路径与保留物身份）冲突。桌面同样反对。

## 双方不变式（任何路径必须保持）

- 删除动作**逐条目**、独立审计回执；
- 高危确认语义（延迟确认+不可恢复明示，007 已裁定）不因全局开关弱化；
- 全局开关=偏好/编排意图，不合并删除的审计责任；
- 未裁决前 v0.2 维持冻结，桌面开关维持「未接线」呈现。

## 桌面推荐

路径 a（M4/M5 即期）：零协议影响，与数据侧倾向一致；确认对话框与逐条目审计
天然契合。若产品侧后续要求 provider 编排保证，再按路径 b 升 v0.3（提案随叫随到）。
