## 2. 内部文档 SemVer

- **Major**：文档结构大改、章节重组、内容方向变化；
- **Minor**：新增章节、补充重要内容，不影响原有结构；
- **Patch**：修正错别字、更新数据、微调措辞。

### 2.1 头部格式

每个受管文档统一使用以下头部：

```
> 文档版本：x.y.z
> 状态：草案 / 已接受 / 冻结 / 已取代（→ 继任者路径）
> 权威语言：简体中文（EN 为镜像，同步至 x.y.z）
> 最近符合性复核：YYYY-MM-DD（仅 T4 需要）
```

T2 契约文档保留其既有的协议/格式版本状态块，文档版本行加在状态块附近，不改动状态措辞。

### 2.2 变更日志节

文档末尾固定 `## 文档变更日志` 节，每版一行（版本、日期、一句话），只留最近 10 条，更早的查
git 历史。Patch 可搭车任意提交；Minor/Major 必须在提交信息中点名文档与版本动作。

### 2.3 双语对

版本号属于"文档对"。ZH 为权威源，EN 镜像须在头部标注同步到的版本；允许 Patch 级瞬时脱节，
Minor 以上必须同批双语。

### 2.4 状态与版本分离

- "冻结"是生命周期状态，不是内容不可变的承诺；冻结后 Patch 允许；
- 冻结文档的**规范性内容**变更 = Major + 明确的解冻裁决记录（谁、何时、为何），且旧版本节保留；
- T2 契约维持更严规则：任何规范变更只升版本号、不原地改。

### 2.5 冻结硬前置

任何契约/协议标注"已冻结"之前，必须已入库：机器可读 Schema（或有正当理由的豁免记录）、
正负例测试向量、至少一端的消费测试。三者不齐时状态只能是"候选"。

### 2.6 登记处

`docs/REGISTRY.md` 是全部受管文档的机器可读表（路径、文档版本、状态、维护方、最近复核日期）。
格式为一行说明加一张 markdown 表：

```
| 路径 | 文档版本 | 状态 | 维护方 | 最近复核 |
```

路径指 ZH 版，EN 镜像随行不单独登记。更新规范见 §3。

### 2.7 可追溯性

每个 M 门的发行说明末尾附"本门接受的文档版本矩阵"（从 REGISTRY 快照），使产品版本 ↔ 文档
版本可互查。

## 3. REGISTRY 更新频率规范（事件驱动，非按协作次数）

- **更新触发器**（仅四种）：① 受管文档 Minor/Major 版本变化；② 文档状态变化（草案→已接受→
  冻结→已取代）；③ 新增受管文档；④ M 门符合性复核后刷新复核日期。**Patch 级修改不动
  REGISTRY**。
- **同批提交**：REGISTRY 行修改搭车引起它的那次文档提交，不产生额外提交、不增加协作往返。
- **频率预期**：按当前节奏约每天 0–3 次单行编辑；状态文件/提案讨论等协作动作**从不触碰**
  REGISTRY（那是 collab/ 的职责，两个机制各管各的）。
- **防漂移靠机器校验而非高频人工**：`collab:brief`（及日后的 CI）校验每个受管文档头部的
  版本/状态与 REGISTRY 行一致，不一致即列入报告。用低成本检测代替预防性高频更新，人只在
  事件发生时写一行。
