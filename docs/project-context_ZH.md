## 项目起源

VUA 最初来自中国大陆 VRChat 玩家面临的三个直接问题：跨境网络和软件下载不顺畅、正版 BOOTH
素材难以浏览和判断适配性，以及以英文界面为主的 Unity/VRChat 制作流程对新手不友好。最早的
设想接近“一键部署环境 + 教学助手”，随后逐步转向以实际任务完成为目标的桌面工具。

一个重要产品观察来自 Avatar 成品交易市场：部分玩家会购买由多种素材拼装而成的 Unity 项目，
其中经常存在未经许可传播付费素材的问题；与此同时，“愿意购买正版，但不会寻找、搭配和装配”
确实是普遍需求。VUA 因此把重点从教程转向合法素材条件下的可复现装配，让用户选择目标组合，
再由程序处理环境、项目、依赖、绑定、菜单、检查和恢复。

## 关键变迁

| 阶段 | 主要方向 | 后续结论 |
| --- | --- | --- |
| 早期原型 | 环境部署、BOOTH 浏览、Modular Avatar 自动改模、性能检查和项目管理 | 教学降为辅助，确定性任务执行成为主线 |
| v0.2 | VUA、AMF 与独立云端 BDB；确立 Recipe-first 和“Avatar 超级工厂”生产隐喻 | VUA、AMF、BDB 成为公开缩写；旧内部代号停止使用 |
| v0.3 | React 桌面端、Overlay、Recipe Schema、Unity Bridge、云端 BDB 管线 | BDB 单次管线承担采集、识别、去重、兼容和发布过多，持续返工；完整浏览体验需要 Chromium、隔离 Session 和下载管理能力 |
| v0.4 重建 | 新仓库、Electron 桌面端、原生 Warehouse、BDL 本地化、第三方插件与运行时集成 | 新仓库成为实现权威，并以清晰模块边界和重新审定的文档为基线 |

云端 BDB 曾尝试建立 BOOTH 商品、兼容关系、VN3、离线数据包和公共 API。实践证明问题不在“完全
无法采集”，而在于把过多识别与清洗目标耦合进同一管线。后来又验证了 BOOTH Library Manager 和
VRC Avatar Explorer：它们可以作为补充来源，但下载、语言、存储、稳定性或交互体验不足以替代
VUA 自己的 Warehouse。最终撤销“不自制浏览和下载”的决定，停止独立 BDB 产品，将相关能力重建
为 AMF 所属的本地 BDL。

桌面端使用 Electron，以获得稳定的 Chromium、多网页视图、隔离 Session 和下载管理能力。
React、TypeScript 与 Vite 继续承担表现层。当前方向增加小型 Node.js Kernel，
通过 VUA 自有边界显式组合可信 Core 模块。Rust Orchestrator 通过可替换的版本化 Provider 接入；
进程内原生与受监督独立进程托管仍是候选。社区插件不共享该可信上下文；Unity Bridge 不变。
Kernel、Core、Plugin 与 External 各自保持明确的权威边界。

## 当前产品定义

VUA v0.4.0 是面向 Windows 的模块化 VRChat 桌面游玩和 Avatar 生产工具包。用户选择“部署环境”、
“配置运行时工具”或“制作某套 Avatar”等目的，VUA 规划并执行必要步骤，保存可检查、可恢复的
任务状态和 Build Record。

核心模块及所有权如下：

1. **Electron 桌面与 Kernel**：Electron 拥有窗口、本地 UI、隔离网页、Session 和下载；Kernel
   拥有启动、可信组合、Gateway 强制和 Provider 托管/监督。
2. **Rust Orchestrator**：计划、批准、持久任务、取消、恢复、适配器协调和 Build Record，通过
   可替换的版本化 Provider 接入 Kernel。
3. **AMF（Avatar MegaFactory）**：Avatar 生产抽象层，包含五个用户阶段：
   - Warehouse：素材发现、授权下载、预览、识别和整理；
   - Recipe：素材组合、参数和操作意图；
   - Assembly：项目与依赖解析、计划和确定性装配；
   - Inspection：功能、性能、依赖、光照和上传准备度检查；
   - Release：项目版本、快照、Build Record 和官方 SDK 上传交接。
4. **BDL（Booth Database Local）**：AMF 私有的本地数据模块，管理商品、文件、协议、别名、兼容
   关系、来源、搜索和 Warehouse 映射；只通过 AMF 应用服务提供能力。
5. **环境与项目管理**：检测和部署 VR/Unity/VRChat 环境，处理 EAC 启动冲突诊断，并管理 Unity
   项目。
6. **Unity Bridge**：使用全球版 Unity `2022.3.22f1` Editor Package 和版本化作业协议执行可测试
   操作；历史 VRChat Editor 项目通过迁移路径接入。
7. **扩展与集成**：Core 模块在 Kernel 自有边界后组合；社区插件使用未来公开能力边界；外部集成不获得
   VUA 内部服务；Overlay 与运行时集成消费稳定服务。

## 稳定产品思想

- **从目标出发**：用户选择想得到的结果，由系统处理传统流程中的“路线和换乘”。
- **Recipe-first**：先选择合法拥有的素材和组合意图，再创建或修改项目。
- **Recipe 不分发素材**：它引用素材身份、参数与规范化操作，不携带付费文件、定制贴图、动作或
  Blueprint ID。接收端只有在合法取得对应素材时才能尝试复现。
- **Build Record**：记录一次生产实际解析出的素材、版本、计划、操作、结果、指纹、警告和恢复点。
- **确定性优先**：可规范化的 Unity 操作通过 Unity Bridge 实现，稳定复现是 VUA 相比临时 Agent
  操作的重要价值。
- **本地优先**：购买会话、订单、下载、付费素材、BDL 数据和生产状态保留在用户设备。
- **能力感知**：面对不同机器、工具版本和第三方能力，界面必须报告真实可用范围并保留人工路径。

Agent 原生操作接口曾被讨论，但尚未成为近期产品核心。当前接受的是稳定插件协议和应用 Gateway；
未来是否增加面向外部 Agent 的正式操作面，需要单独的安全、权限与协议决策。

## 当前依赖与兼容边界

项目管理有三条明确路径：

1. VUA 基于 `vrc-get` 自建并维护包管理器；
2. 兼容由 ALCOM 管理的项目；
3. 兼容由 VCC 管理的项目。

后两项是项目兼容，不代表嵌入、复刻或完整支持 ALCOM/VCC 应用。任何写入都必须先检测项目格式、
版本、锁定状态和适配器能力。

计划中的运行时集成包括 SlimeVR Server、VRCFaceTracking 和 OpenVR Space Calibrator。集成同时
考虑“许可证允许时的可选托管”和“连接用户已有安装”两种模式。第三方组件进入发行包前必须逐项
审查许可证、再分发、更新来源和签名。该方向已经延期到正式版 `1.0.0` 发布后，正式版以前不进入
开发排期。

BLM、VAE 是 AMF 素材获取与内容管理的可选适配器；它们不取代 VUA 原生路径，也不能直接写入
BDL。VRCX 只考虑公开、明确的导入导出或启动边界，不全量复制其社交与账号能力。

## 安全与法律底线

- 不绕过 BOOTH 或其他平台的购买、登录、付费、年龄和访问控制。
- 不提交付费素材、用户 Unity 项目、Cookie、令牌、订单、生产数据库或含隐私的日志。
- 远程网页不能访问 Node.js、VUA Gateway、文件系统、凭据、Orchestrator 或插件宿主。
- 插件不能直接访问 BDL、主数据库、Electron Session 或 Unity Editor 内部对象。
- EAC 功能仅限启动冲突诊断、残留游戏进程恢复、官方 repair 和重启引导；不得停止或卸载驱动、
  修改反作弊文件、注入进程或提供绕过能力。
- Avatar 最终登录和上传继续使用 VRChat 官方 SDK Panel。

## 迁移资产与历史债务

- 旧 `VRC_Ultra_assistant` 与 `VUA_BDB` 作为历史证据保留；当前仓库是实现权威。
- BDL 采用全新的本地设计；旧 BDB 代码、Schema、管线、部署与离线包保留在历史归档中。
- `GLM/orchestrator` 的状态机、恢复/幂等、端口、测试和固定向量具有复用价值；当前迁入基线曾通过
  138 项自动测试和 Clippy，但其语言、目录和旧通信层不是产品约束。
- React 交互、可访问性测试、Token 与组件经验可作为迁移参考；现行桌面端统一使用 Electron 壳与权限模型。
- Unity Bridge 的 C# Package、Schema、合成测试和全球版 Unity `2022.3.22f1` 本地验证具有保留价值；公开仓库使用
  合成 Avatar、可移植路径和可重复的自动验证场景。
- 旧美术与 UI/UX 文档作为低权威参考，由真实 Electron 页面和可执行测试重新验证。

## 仍未裁决或尚未完成

- 发布签名和更新机制；
- Orchestrator 托管决议、Provider 传输/错误/关闭行为与打包；
- BDL 实体身份、SQLite Schema、页面观察格式、协议表示和兼容证据模型；
- 插件的执行隔离模型及是否建设插件目录或市场；
- Electron 首个真实纵向切片、正式 CI 与安装包；
- 包管理三路径的真实能力矩阵和项目兼容测试；
- Recipe、Build Record 与 Unity Bridge 后续版本的真实 Avatar 冒烟测试。

仓库采用 Apache-2.0，公开贡献政策已经确定；具体发行包的第三方再分发审查仍按每次构建单独完成。

## 给后续主 Agent 的工作原则

1. 先确认任务归属，再只读取对应规范；不要一次加载全部旧研究和迁移资料。
2. 产品边界变化先改唯一规范来源，再修改架构、协议、计划和实现。
3. BDL 的任何能力都必须经 AMF 暴露；浏览下载属于 AMF 素材获取模块。
4. Rust 是当前 Orchestrator 实现；托管方案由独立 ADR 按证据选择。Gateway 与持久格式只使用
   版本化产品契约。
5. 项目管理始终区分 VUA 自建 `vrc-get` 包管理器、ALCOM 项目兼容和 VCC 项目兼容。
6. 优先交付带真实输入、失败路径、恢复验证和可执行测试的小型纵向切片。
7. 新实现不得因为迁移代码已经存在，就跳过契约、许可证、安全和产品边界审查。
