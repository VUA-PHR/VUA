# BDL v2 能力清单:兼容性/依赖关系分析

[English](bdl-v2-capability-list_EN.md) | [简体中文](bdl-v2-capability-list_ZH.md)

> 状态:草案——待产品所有者裁决;未经接受前无规范效力
> 范围:BDL v1 冻结边界(`bdl-v1-boundary`)之上的未来能力层
> 前提:v1 的 IN/OUT、schema 准入规则、抓取纪律继续全部有效;本文只新增,不推翻
> 更新:2026-09-05

## v2 要回答的问题

v1 冻结了"存什么、筛什么";v2 回答"**关系怎么来、怎么用**"——即旧云端 BDB 想一步登天
实现的兼容性/依赖分析。旧 BDB 的失败路径是:先建全网巨型关系库,再让管线去填。v2 的反命题:

**关系按需生长——用户搜了哪些,才获取哪些;获取到哪些,才分析哪些。**

## 三条不变式(对旧 BDB 失败模式的逐条规避)

1. **不预建矩阵。**关系图从用户已有的观测增量生长。没有"先爬全量再分析"的阶段,也没有
   为未来矩阵预留的膨胀字段;每条边在写入时就必须回答它服务于哪个查询。
2. **不自动断言。**分析产物永远是"证据 + 出处 + 确认状态"三元组,可筛选、可排序、可
   量化覆盖;阻断性的兼容结论必须经用户确认(与 v1 IN-3 的人工确认姿态一致)。自动覆盖
   率是旧 BDB 的失败指标(语料证据:coverage "passed" 仅 7.6%),不是 v2 目标。
3. **不新增抓取器。**抓取永远是用户动线内的 AMF 素材获取行为:可见、可取消、沿用每请求
   6 秒纪律与 robots.txt 留痕。BDL 只消费 AMF 已验证的来源观察(`docs/architecture/bdl_ZH.md`
   的既有边界),后台自主刷新不存在。

## IN——能力

| # | 能力 | 说明 | 前置/证据来源 |
| --- | --- | --- | --- |
| V2-1 | 关系证据的规范化存储 | 作者声明的依赖与兼容(正文、附加段落、子商品名)升级为带完整出处的一等记录:页面区域、`content_hash`、`observed_at`、`processor_version`、抽取规则版本 | 抽取规范 v0.2 开放项"兼容性/依赖抽取规则"按同一方法论成文;v1 IN-3 的语料覆盖证据(40%) |
| V2-2 | 用户驱动的关系扩展(一跳深挖) | 用户查看的商品声明"对应/兼容 X"时,AMF 素材获取可**提议**把 X 的商品页纳入获取动线;用户确认才发生;观测照常经验证入 BDL | 既有 AMF 浏览/下载端口;无新抓取面 |
| V2-3 | 本地关系图(增量、版本化) | 两类边:商品↔商品(声明兼容/同系列)、商品↔包(作者声明的依赖);每条边携带证据类型、确认状态、出处指针;以版本化 schema 迁移落地,不在 v1 表上就地变形 | V2-1;v1 schema 准入规则的扩展(见下) |
| V2-4 | 别名/实体解析表**消费** | v1 OUT 预留的"联网不定期更新的表"在此作为证据输入被消费:本地缓存、带许可与出处、可整体失效重载;**不本地自动派生别名**——从页面结构找规律仍是失败模式 | 待裁决:表的来源、维护方、许可、缓存与失效策略 |
| V2-5 | 依赖证据 → Recipe 供给 | "此衣装需要 lilToon"作为证据记录供给 Recipe 的依赖声明(B3 裁定:依赖声明归 Recipe 层);BDL 只供证,不声明依赖 | Recipe v0.3 依赖声明的消费接口 |
| V2-6 | 关系查询面 | 按商品的关系视图、按 Avatar 找衣装、按依赖找缺口;全部只基于本地已观测数据,缺口如实报告"未观测"并转为 V2-2 的提议来源 | V2-3;五个 v1 边界查询继续通过 |

## OUT——v2 仍然不做

- **全库预抓取与预建全网兼容矩阵**——旧 BDB 的原失败路径,永不出现在计划里;
- 自主/后台爬取、守护进程式刷新、分布式抓取(继承 v1 OUT);
- 自动断言兼容并据此阻断流程——确认状态机之后才有资格讨论;
- 从页面结构自动发现别名规律(别名只能来自联网表消费或人工修订);
- 运行时兼容判定——"装上是否真能跑"属于 Assembly/Inspection 的验证证据,BDL 只管页面证据;
- 公共 API、前端服务(继承 v1 OUT;读取面扩权需另行接受契约)。

## 分析方法边界

- **先真实 HTML,后成规则**:兼容/依赖抽取规则按抽取规范 v0.2 的同一流程产生——从本地
  语料的真实商品页(含黄金锚定商品及其声明对象)归纳,版本化成文,再以黄金断言 + 合成夹具
  重写管线。不存在先写规则再找例子反着凑。
- **分析配方是本地代码**:清洗、匹配、确认状态机都是本地实现,不从网络获取"分析逻辑"。
- 每条关系必须能回答四个问题:哪次观察、哪个页面区域、哪条规则、谁确认。

## schema 准入(v1 规则 + v2 追加)

- 继承 v1:字段必须回答"IN 表哪一行、哪个筛选/映射查询需要它"。
- v2 追加:关系边必须回答三件事怎么存——**证据类型、确认状态、出处指针**;没有证据链的
  关系行不允许存在。别名缓存表必须带许可字段与整体版本字段。

## 边界查询(v2 schema 冻结前必须全部通过)

夹具 = 两个黄金锚定商品 + 其声明对象的本地存档 + 明确标注合成的关系行(沿用 v1 验证纪律)。

1. 给定 Avatar,列出本地已观测的声称兼容衣装,按确认状态分层;
2. 给定衣装,列出作者声明的包依赖,可直接供给 Recipe;
3. 给定任一关系,追溯完整出处链(观察 → 页面区域 → 规则 → 确认者);
4. 给定搜索词,报告本地覆盖与缺口,缺口可转为获取提议;
5. 别名缓存行的许可与来源版本可追溯、可整体失效。

## 时序与前置

- **不阻塞 v1/B4**:B4 落地最小 BDL SQLite schema(即 v1 边界);v2 关系层作为版本化迁移
  跟随其后,不在 B4 范围内抢跑。
- 前置研究项(按依赖顺序):
  1. 兼容/依赖抽取规则成文(抽取规范开放项第 2 条,方法论已定);
  2. 联网别名/兼容表的来源与许可裁决(V2-4 的唯一未决项);
  3. Recipe v0.3 依赖声明对 BDL 证据的消费接口(B5 线对齐)。
