# BDL v1 功能边界

[English](bdl-v1-boundary_EN.md) | [简体中文](bdl-v1-boundary_ZH.md)

> 状态:产品所有者裁决冻结(2026-09-04)
> 范围:BDL v1 Spike schema 与管线设计输入
> 规范效力:界定 BDL v1 存什么、筛什么;模块所有权以 `docs/architecture/bdl_ZH.md` 为准

## 为什么要有这条边界

旧云端 BDB 的停滞源于愿景超出管线: schema 反复重修膨胀,流程错误地要求两层管线覆盖海量
corner case,前端和中台都出初稿时数据清洗仍未完成。因此 BDL v1 先划定明确边界,字段只从
"边界 + 真实语料格式"推导,SQLite 等基础设施最后再建。

## IN——能力与语料证据

| # | 能力 | 语料证据 |
| --- | --- | --- |
| 1 | 商品/子商品/店铺观测的规范化存储 | 135,973 条 record v2(135,829 complete / 144 墓碑),基于真实 HTML 的抽取规范(锚定商品 Meiyun/Nemesis) |
| 2 | 条款观测:正文中的 VN3 与普通条款链接,保留出处,人工提取,可筛选 | L2 条目 `active_terms` 覆盖 99% |
| 3 | 声明式兼容线索(正文/子商品名),人工确认后可筛选 | 覆盖 40%;coverage "passed" 仅 7.6%——自动覆盖正是旧的失败模式 |
| 4 | 已下载工件 → 来源商品映射 | 锚定 `material_identity` |
| 5 | 对上述全部内容的搜索与筛选 | a1-smoke 规范化形状(100 条,30 个恒满字段) |

## OUT——但都有明确的未来归属

- **自动别名/实体解析**(一个 Avatar 多个名字)与**兼容矩阵构建**(多个 Avatar 衣装兼容性
  相同)仍是 VUA 整体产品的重要组成,但未来走**两张联网不定期更新的表**。BDL v1 不再尝试
  从奇形怪状的页面结构里自动找规律。
- **从 Google Docs/Drive 自动提取 VN3**——待 Google 自动访问政策调研;其后候选方向是把
  成批链接交给 LLM(如 Gemini)处理。v1 仅人工提取,记录 `source_url` 与可空的内容哈希。
- **公共 API、前端服务、分布式爬取、自主爬取。** BOOTH 抓取节奏沿用旧爬虫实测:每请求
  6 秒,且只用于明确批准的小样本重验任务。
- **死字段**,语料否决:`etag`、`last_modified`(135,973 条 100% 为 null)、
  `source_updated_at`(无稳定 BOOTH 来源——既定决定)。

## Schema 准入规则

一个字段进入 schema 前必须回答:"IN 表里哪一行、哪个筛选/映射查询需要它?",且其证据要么
是抽取规范 + 真实语料字段,要么是 IN 行的查询需求。提案 schema 见
`schemas/bdl-spike/v0.1/schema.sql`。

## 验证

schema 已对本地语料做了演练:100 条 a1-smoke 规范化记录(标记
`legacy.a1-smoke-20260831`——仅作形状验证,不是可信事实),加两个黄金锚定商品的
record v2 可信行,以及明确标注为合成的条款/兼容/工件行。五个边界查询全部通过:
分类+搜索筛选、VN3 条款筛选、人工确认兼容筛选、工件→商品反查、逐商品出处追溯。

装载发现的身份要点:语料 `product_id` 是带命名空间的身份(`booth:<native_product_id>`),
子表必须用同一命名空间键。

## 开放项

- Google Docs/Drive 自动访问政策调研(决定 IN-2 的设计)。
- `source_published_at` 经裁决准入(渲染页位置已证实);在具备渲染抓取能力前取值恒为 null。
- 抽取规范升格:真实 HTML 抽取规则(选择器、兜底、负知识)正在整理为版本化文档;识别管线
  随后以两个黄金锚定商品 + 合成夹具从零重写。
