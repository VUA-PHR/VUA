# ADR：Orchestrator 采用受监督独立进程 Provider

[English](orchestrator-supervised-provider_EN.md) | [简体中文](orchestrator-supervised-provider_ZH.md)

> 状态：已接受
> 日期：2026-09-02
> 决策者：产品所有者
> 范围：B2 Orchestrator 托管

## 决策

生产实现采用受监督独立 Rust 进程，通过版本化、有界 JSONL 管道连接 Electron Main。进程内原生
Provider 保留为接口可替换性说明，不进入当前生产实现，也不为比较而引入 napi-rs 依赖。

项目互斥身份采用“操作系统规范化最终路径的 SHA-256 摘要”。明文项目路径不得写入任务数据库的
租约键。

## 生产后果比较

| 方案 | 崩溃与关闭 | 打包、调试与延迟 | 产品后果 |
| --- | --- | --- | --- |
| 进程内原生 Provider | Rust panic/内存错误可带走 Electron Main；原生库不能真正卸载，关闭只能逻辑停用 | 少一个进程和封帧，但增加 Node ABI、napi-rs、DLL 装载与签名组合；单次调用延迟最低 | 对本地长任务的可恢复性不利，生命周期边界模糊 |
| 受监督独立进程 | 崩溃被隔离；退出码、握手、重启、Job Object 和强制关闭恢复边界可观察 | 一个独立 EXE 和有界管道；诊断可分 stderr；有进程/序列化开销 | 与 SQLite 权威恢复、可替换托管和 Electron 安全边界一致 |

VUA 的实际瓶颈是 Unity、文件和网络操作，而不是本机小型控制消息。受监督进程的封帧开销不会改变
用户可感知路径；其崩溃隔离和真实可停止边界更符合“任务可恢复、UI 不承载业务核心”的产品定义。

项目身份方面，保存明文规范路径容易把用户名与素材目录泄露到数据库/诊断；项目内 UUID 会修改用户
项目且在首次识别前不存在；仅使用用户输入路径又会因相对路径、符号链接和大小写别名破坏互斥。
规范化路径摘要不写项目、不会泄露明文，并让同一现存目录稳定命中同一租约。代价是目录移动后视为
新项目，此时重新 Inspect 是安全且诚实的行为。

## 验证与移除

B2 已覆盖握手、查询、事务后事件、持久取消幂等、重启恢复、意外退出、显式重启、受限环境、帧大小、
单实例锁、等待/强制关闭和 Windows Job Object 初始化。开发环境完成 TypeScript 监督端到 Rust EXE
再到 SQLite 的真实往返；同机 debug 构建的 50 次空 `task.list` 往返样本中位数为 0.155 ms、p95 为
0.337 ms。该样本只证明控制消息开销量级，不是发行性能承诺。正式签名和安装包验证属于 B10/M10
发行制品门。

移除独立进程不要求修改应用契约：新 Provider 必须实现同一 `OrchestratorProviderV01`、通过相同
Gateway/恢复行为测试，并在空闲安全边界替换。届时可删除进程封帧与监督适配器；SQLite 格式和应用
契约不随托管形态变化。
